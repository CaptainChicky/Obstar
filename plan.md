## Reading the references: unit and convention notes

| quantity | diep | ours | conversion |
|---|---|---|---|
| tick | `mspt = 40` (`diepcustom/src/config.ts:26`) | `REF_TICK_MS = 40` | **1:1, no time conversion** |
| length | 1 gu = 50 du | 1 gu = 28 units | **du → ours: × 0.56** |
| speed | du/tick | units/ref-tick | × 0.56 |
| speed | du/tick | u/s | × 14 (`× 0.56 × 25`) |
| tank base radius | `baseSize = 50` du (`TankBody.ts:66`) | `28` | 50 du = 1 gu = 28 ✓ |
| level exponents | `1.01^(L−1)`, `1.015^(L−1)`, L 1-based | `1.01^this.level`, `this.level` 0-based | **identical** ✓ |
| barrel/bullet multipliers | `TankDefinitions.json`, 1.0 = base | `TanksConfig.js`, 1.0 = base | **1:1** ✓ |

**The `lib/tick.js` category for every new constant is called out per step.** Getting it wrong does
not fail loudly (PENDING nuance 39).

**The friction ordering difference, stated once so no step re-derives it.** diep applies
`v += A; x += v; v *= 0.9` (`diepcustom/src/Entity/Object.ts:265-275`, `applyPhysics`). We apply
`v = (v + A)·F; x += v` (`public/SHARE/Physics.js`'s `stepBody`). Both have steady state `10·A`
— ours only because `F = 10/11` was *derived* to make it so. The two differ only in **transient**:
diep's velocity error decays ×0.9/tick, ours ×0.909/tick (e-fold 0.38 s vs 0.42 s). This is why
`Physics.FRICTION = 10/11` is **not** contradicted by diep's 0.9 for tanks — but it *is* the whole
story for bullets, whose terminal speed is `thrust × F/(1−F)` and therefore 22.0× thrust at our
`BODY_FRICTION` against 10× at diep's 0.9. See Step 9.

### Step 5: The damage model becomes diep's — `damageReduction()` out, multiplier table + proration in
- **Resolves:** contradiction C1. **Decided by the user, 2026-07-31:** `damageReduction()` was an
  attempt to approximate diep; the reference says diep has no such term, so it goes and diep's real
  model goes in. This reopens PENDING #18's `dr` bullet (SHIPPED, but on a premise now known false)
  and #17's lethality call.
- **Reference:** `diepcustom/src/Entity/Live.ts:67-84`, the whole of diep's damage resolution:
  ```ts
  let common = Math.max(entity2.minDamageMultiplier, entity1.minDamageMultiplier);
  common *= Math.min(entity2.maxDamageMultiplier, entity1.maxDamageMultiplier);
  const dF1 = (entity1.damagePerTick * common) * entity2.damageReduction;   // 1 -> 2
  const dF2 = (entity2.damagePerTick * common) * entity1.damageReduction;   // 2 -> 1
  const ratio = Math.max(1 - entity1.health / dF2, 1 - entity2.health / dF1);
  entity1.receiveDamage(entity2, dF2 * Math.min(1, 1 - ratio));
  entity2.receiveDamage(entity1, dF1 * Math.min(1, 1 - ratio));
  ```
  `damageReduction` there is **binary** — `1.0` normally, `0.0` for spawn protection / godmode /
  Arena Closers (`TankBody.ts:104, 199-208`). No Body-Damage-points term exists on the receiving side
  anywhere in the reference.

  The multiplier table (`Live.ts:46-51` defaults, overridden per class):

  | entity | `minDamageMultiplier` | `maxDamageMultiplier` | citation |
  |---|---|---|---|
  | default / shape | 1.0 | **4.0** | `Live.ts:50`, `AbstractShape.ts:79` |
  | tank body | 1.0 | **6.0** | `TankBody.ts:100` |
  | bullet | **0.25** | **1.0** | `Bullet.ts:92-93` |
  | drone / trap | 1.0 | **1.0** | `Drone.ts:96-97` |
  | team base | 1.0 | 1.0 | `TeamBase.ts:63-64` |

  That table reproduces every ratio we already hardcode: tank-vs-shape `min(6,4) = 4`; tank-vs-tank
  `min(6,6) = 6`, **exactly our `TANK_BODY_DAMAGE = 1.5`**; anything-vs-bullet `min(x,1) = 1`,
  **exactly our `PROJECTILE_BODY_DAMAGE = 0.25`** relative to the vs-shape baseline. The one part we
  do not model is `max(min1, min2)`, which only bites bullet-vs-bullet.
- **Current code:**
  - [entities/Player.js:546](entities/Player.js#L546) — `damageReduction() { return 0.4 / (1 + 0.2 * this.upNb[5]); }`,
    multiplied in at all three `collision()` damage sites plus `entities/Bullet.js`'s two.
  - `this.damage = 13.852814` is the **vs-shapes** figure with diep's ×4 already baked in;
    `TANK_BODY_DAMAGE = 1.5` and `PROJECTILE_BODY_DAMAGE = 0.25` re-derive the other two columns at
    their own sites.
  - No proration anywhere — both sides take full per-tick damage and the dead one dies.
- **Change:**
  1. **Delete `damageReduction()` and every call site.** diep's binary equivalent is already
     expressed by our short-circuit guards (spawn `shield`, `dev.god`, `this.closer`), which return
     before the damage line — that *is* `damageReduction = 0`. So in practice this is a deletion.
  2. **Re-express the three magnitude constants as one multiplier table.** `this.damage`'s base moves
     `13.852814 → 3.4632035` (÷4, diep's `damagePerTick` convention) and the per-point step
     `2.770563 → 0.69264` with it; a shared `common(a, b)` helper applies
     `min(maxMult_a, maxMult_b)` at every damage site. `TANK_BODY_DAMAGE` and
     `PROJECTILE_BODY_DAMAGE` are **retired into the table**, not kept beside it. Numerically a no-op
     for tank-vs-shape and tank-vs-tank — prove that with a `clientDiff` isolation pass.
  3. **Add `max(min1, min2)`** — bullets carry `minDamageMultiplier = 0.25`, everything else 1.0.
     Only changes bullet-vs-bullet.
  4. **Add proration.** One shared resolver: compute both `dF`s, take
     `ratio = max(1 − hpA/dFb, 1 − hpB/dFa)`, scale both by `min(1, 1 − ratio)`. Our pass calls
     `collision()` on both sides sequentially (nuance 44), so the pair must be resolved **once** —
     the natural home is `rooms/Room.js`'s pair loop, with the per-kind arms keeping only the
     non-damage physics (knockback, overlap, bounce, destroy flags). **This is the one genuinely
     structural piece of the step**; budget for it, and it is fine to land 1-3 first and 4 second.
- **Unit conversion:** none — every multiplier is dimensionless and the `4.84848 ≡ diep's 7` anchor is
  untouched. Damage stays `tick.perTick()` (a per-reference-tick contact event).
- **Test impact:** the largest of the pre-bullet steps. `test/rooms.js`'s base-drone-vs-shape test and
  every damage assertion re-baseline. `test/clientDiff.js`'s golden moves substantially (nuance 34's
  "how long one LIVES"). **Isolate in three passes**: (a) `dr` deletion alone, (b) the multiplier
  re-expression alone — must be a provable no-op outside bullet-vs-bullet, (c) proration alone.
- **Moves:** `lib/config.js`'s `BASE_DRONE_DAMAGE` and `rooms/Tag.js`'s Arena Closer damage both ride
  `this.damage`'s base and follow the ÷4 (their *effective* output is unchanged).
- **Balance consequence, stated not hidden:** deleting `dr` makes every source of damage to a tank
  **2.5× stronger** at 0 Body Damage points and **6× stronger** at 7 (the term currently runs 0.4 down

### C1 — `damageReduction()` has no counterpart in diep *(highest impact)*
[entities/Player.js:546](entities/Player.js#L546) applies `dr = 0.4 / (1 + 0.2 × bodyDamagePoints)`
at all three `collision()` damage sites — so a tank takes **40 %** of nominal damage at 0 Body Damage
points and 16.7 % at 7. PENDING #18 and HANDOFF §3 both present this as "diep's `dr` rule".

**diepcustom has no such term.** `LivingEntity.damageReduction` (`Live.ts:44`) is a **binary
invulnerability multiplier** — `1.0` normally, `0.0` during spawn protection, godmode, and for Arena
Closers (`TankBody.ts:104, 199-208`). The only damage scaling in diep is
`common = max(minMult₁, minMult₂) × min(maxMult₁, maxMult₂)` (`Live.ts:74-75`), which is exactly the
4 / 6 / 1 shape-vs-tank-vs-projectile family we already model as `×4` baked into the base plus
`TANK_BODY_DAMAGE` and `PROJECTILE_BODY_DAMAGE`. There is no Body-Damage-points term on the receiving
side at all.

**Effect if adopted:** every source of damage to a tank becomes **2.5× stronger** at 0 Body Damage
points. Combined with our bullet damage being `4.84848 ≡ diep's 7` on a 50 HP tank, our current
time-to-kill is roughly **3.6× diep's**. So `dr` is not a small fidelity gap — it is most of why
combat here is slower than diep's.

Also unmodelled and part of the same question: diep's **mutual proration** (`Live.ts:78-84`,
README §5) — when a body dies mid-tick, both sides' damage that tick is scaled by the same surviving
fraction. We apply full per-tick damage to both sides and let the dead one die.

**RESOLVED — this is now Step 5, not a flag.** The user's call, 2026-07-31: *"damagereduction was me
trying to approximate diep, but if that one is wrong then probably remove that and implement what diep
have."* Removing `dr` is a lethality change of the same magnitude as the one PENDING #17 made

### C2 — Knockback scales with the Bullet Damage stat; our column is frozen at 1 point
PENDING #16 is SHIPPED and marked do-not-re-fix: `weight` is `physics.html`'s Knockbackfactor table
× 5.25, consumed as `tick.impulse(weight / 3 × 1.6)`.

diep computes it (`Bullet.ts:88`, README §4.3.2):
```
pushFactor    = (7/3 + bulletDamagePoints) × bullet.damage × bullet.absorbtionFactor
knockback (du/tick) = receiver.absorbtionFactor × pushFactor
```
**Our column's *shape* is exactly right** — check it: Basic `(7/3+1)×1 = 3.333` → `/5` = 0.666 gu
(our `weight 3.5`); Twin `(7/3+1)×0.65 = 2.167` → 0.4333 gu (our `2.275`); Destroyer
`(7/3+1)×3×0.1 = 1.0` → 0.2 gu (our `1.05`). Every entry is `weight = 5.25 × pushFactor/5`, uniformly.

**Two findings fall out of that:**
1. **`physics.html`'s table was measured at 1 Bullet Damage point, not 0.** Our column reproduces it
   exactly at `bd = 1`. So the correct *base* (0-point) knockback is **0.7×** our current values, and
   the 7-point value is **2.8×** — a **4× span** that we do not model at all.
2. **The absolute delivery is exact at that point.** Our `weight/3×1.6` gives Basic `1.8667`
   units/ref-tick; diep at `bd = 1` gives `3.333 du/t × 0.56 = 1.8667` — **identical** ✓, and both
   integrators put the total displacement at `10 × A`. **The tank-body constant `4.48` is exact too**
   (see confirmations). So there is one finding, not two: the magnitude is right at `bd = 1`, and the
   entire missing piece is the `(7/3 + bd)/(7/3 + 1)` factor — 0.7× at 0 points, 2.8× at 7.

**If it is ever taken:** replace `tick.impulse(other.weight / 3 * 1.6)` with
`tick.impulse(other.weight * 0.112 * (7/3 + shooterBdPoints))`, which reduces to the current
expression at `bd = 1`. It needs the bullet to carry its shooter's Bullet Damage point count (it
already carries `weight`, `push`, `damage`, `pene` — one more field). **Not a planned step**: #16 is
do-not-re-fix, and this is a real balance change on top of Step 2's Bullet Damage slope.

Also unmodelled: diep's **receiver-side `absorbtionFactor`** (README §4.3.1 — Pentagon 0.5, Alpha
0.05, small Crasher 2.0, large Crasher 0.1, bosses/Mothership 0.01, Arena Closers and Maze walls 0,
drones 4). We use a `weight` mass divisor on shapes (1 / 4 / 100) — the same idea on a different axis.
This is nuance 44's "left open on purpose: the tank-vs-shape arm has the same gap"; the reference now
